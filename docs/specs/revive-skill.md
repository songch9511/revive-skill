# Revive 스킬 스펙 (초안 v0.6)

> 상태: 초안 · 작성일 2026-11-22 · 근거: 확정된 의도 정리(인터뷰 결과)

## 1. 목적과 성공 기준

- **목적:** 출시 전에 멈춘 바이브코딩 프로젝트를 진단하고, 살릴지 판정한 뒤, 첫 결제까지 끌고 간다.
- **성공 기준:** 모르는 사람에게서 받은 **첫 결제 1건**. 출시는 중간 단계일 뿐이다.
- **또 다른 정상 종료:** 판정 결과 사용자가 "접기"를 골랐고, 회고 문서가 남은 상태.
- **기준 시장:** 글로벌(영어권, 미국 기준). 결제, 랜딩·카피, 출시 채널을 모두 이 기준으로 안내한다.
  - 사용자와의 대화는 사용자의 언어로 한다.
  - 고객에게 보이는 산출물(랜딩 페이지, 카피, 출시 글)은 영어로 만든다.

## 2. 트리거와 비대상

- **트리거:** 사용자가 포기했거나 멈춘 프로젝트 레포에서 `/revive`를 실행하거나 "이거 다시 살리고 싶어"라고 말할 때.
- **비대상:**
  - 새 아이디어를 처음부터 발굴하는 일
  - 이미 결제가 발생한 이후의 성장(반복 매출, 광고 집행)
  - 법률·세무 자문
  - 한국 전용 절차와 채널: 국내 PG 심사, 사업자등록, 원화 정산, 한국어 랜딩·카피, 국내 커뮤니티 출시. Revive는 글로벌 기준으로만 안내하고, 한국 사용자는 직접 처리한다.

## 3. 구조

| 레이어 | 모델 | 맡는 일 |
|---|---|---|
| 오케스트레이터 | 그 에이전트의 최신 최상위 모델 (예: Opus 5.5) | 사용자와 대화, 진단, 판정, 계획, 체크인, 결과 검증 |
| 실행 레이어 | 한 단계 낮은 모델 세션 (예: Sonnet 5.5) | 작업 단위 구현. 오케스트레이터가 §6의 순서로 고른 스킬을 로드해 실행 |

- 실행 레이어는 계획 단계(0~3)에서는 꺼져 있다. 사용자가 첫 결제 경로(단계 3)를 승인하면 켜진다.
- 오케스트레이터는 코드를 직접 대량으로 쓰지 않는다. 작업을 쪼개 실행 레이어에 넘기고, 돌아온 결과를 검증한다.
- 사용자가 실행 레이어를 끄면 오케스트레이터가 같은 스킬 라우팅으로 직접 실행한다.
- 실행 레이어는 사용자와 대화하지 않는다. 스킬 감지, 설치 제안, 사용자 확인은 오케스트레이터가 한다.
- 모델 이름은 하드코딩하지 않는다. "최상위"와 "한 단계 아래"라는 상대적 등급으로만 정하고, 사용자가 덮어쓸 수 있다.

## 4. 단계 흐름

```
0 정찰 → 1 진단 인터뷰 → 2 판정 → 3 첫 결제 경로 → 4 실행 루프 ⇄ 5 체크인 → 종료
                                 └─ 접기 선택 → 회고 → 종료
```

각 단계는 **완료 조건**을 만족해야 다음 단계로 넘어간다. 단계가 바뀔 때마다 상태 파일(§5)을 갱신한다.

### 0. 정찰 (Recon)

사용자에게 묻기 전에 레포에서 사실을 먼저 모은다.

- 마지막 커밋 날짜, 마지막 몇 개 커밋 메시지, 커밋 빈도가 꺾인 시점
- 미완 브랜치, `TODO`/`FIXME`, 반쯤 만든 기능
- README와 랜딩 페이지 유무, 배포 설정 유무, 결제·인증 연동 유무
- 실행 가능한지 여부 (빌드/실행을 한 번 시도한다). 실패하면 명령과 오류 메시지를 사실로 기록한다. 정찰에서는 고치지 않고, 복구는 실행 루프의 첫 작업으로 잡는다(§6 빌드·의존성 복구).
- **레포 외 자료:** 사용자가 설정한 외부 자료(노션 페이지, 메모, 기획 문서 등)도 읽는다.
  - 읽을 자료는 `state.md`의 `sources` 항목에 사용자가 지정한 것만 대상으로 한다. 지정하지 않으면 레포만 읽는다.
  - 해당 커넥터가 연결되어 있지 않으면 연결을 안내하고, 레포만으로 진행한다.
  - 외부 자료에서 나온 사실은 출처를 함께 적는다.

#### 아키텍처 도식화

정찰의 일부로 코드 전체와 아키텍처를 도식으로 그린다. 목적은 두 가지다. 비효율과 개선점을 찾기 쉽게 하고, 막혔을 때 어디가 문제인지 빨리 짚기 위해서다.

- **산출물:** `.revive/architecture.md`. 도식은 Mermaid로 그린다. 텍스트라서 에이전트가 다시 읽고 고칠 수 있고, GitHub에서는 그림으로 보인다.
- **그릴 것:**
  1. **시스템 개요:** 화면, 서버, 데이터 저장소, 외부 서비스(인증, 결제, 호스팅, AI API)와 그 사이의 연결
  2. **코드 구조:** 디렉터리·모듈 단위의 의존 관계와 진입점
  3. **핵심 흐름:** 방문 → 가입 → 핵심 기능 → 결제까지의 요청과 데이터 흐름. 끊긴 지점을 표시한다.
- **규칙:**
  - 코드에서 확인한 것만 그린다. 노드마다 근거가 되는 파일 경로를 단다.
  - 노드의 상태를 구분해 표시한다: 동작함 / 미완성 / 깨짐 / 안 쓰임.
  - 도식 하나에 노드가 20개를 넘으면 나눠 그린다.
- **도식에서 뽑는 것:** 비효율·개선 후보 목록. 중복 구현, 안 쓰는 코드와 의존성, 순환 의존, 한 파일에 몰린 책임, 불필요한 외부 호출을 찾는다. 후보마다 파일 경로와 근거를 적는다.
- **쓰는 곳:**
  - 진단 인터뷰(단계 1)의 질문 근거
  - 판정(단계 2)의 "남은 인사이트" 가운데 재사용할 코드
  - 첫 결제 경로(단계 3)의 최소 범위
  - 실행 루프(단계 4)의 디버깅
- **범위 제한:** 개선 후보 가운데 첫 결제에 필요한 것만 마일스톤에 넣는다. 나머지는 기록만 하고 손대지 않는다.
- **수행 주체:** 오케스트레이터가 지시하고 수행한다. 레포가 크면 읽기 전용 탐색 에이전트에 나눠 맡길 수 있다. 코드를 고치지 않으므로 실행 레이어가 꺼진 계획 단계에서 수행한다.

**완료 조건:** "확인된 사실" 목록이 상태 파일에 기록되고, `.revive/architecture.md`가 작성됨. 추측은 목록과 도식에 넣지 않는다.

### 1. 진단 인터뷰

Revive 안에 내장한 인터뷰 절차로 진행한다. 별도 스킬로 분리하지 않는다. 이 절차는 interview-me를 Revive용으로 맞춘 것이며, 출처 표기는 §7을 따른다.

- 한 번에 질문 하나만 하고, 질문마다 추측과 확신도를 붙인다.
- 질문은 정찰에서 모은 사실에 근거한다. 예: "3월 12일 결제 연동 브랜치를 만들고 커밋이 멈췄는데, 여기서 막혔나요?"
- 원인 분류는 수요 확신 상실 / 기술적 벽 / UI·UX 불만 / 의욕·우선순위 / 기타. 원인은 여러 개일 수 있다.
- **결정적 원인**과 **핑계**를 구분한다. 판별 질문: "그 문제가 오늘 해결된다면 내일 출시하겠는가?" 아니라고 답하면 그 원인은 결정적 원인이 아니다.

**완료 조건:** 결정적 원인 1~2개를 사용자가 인정함. 또는 질문을 8개쯤 거쳐도 확신도가 오르지 않으면 그 사실 자체를 판정에 넘긴다.

### 2. 판정 (Verdict)

진단 단계와 달리 **추측과 얼버무림을 쓰지 않는다.** 바이브코더는 대부분 자기가 뭘 원하는지 모른다는 것을 전제로 한다.

판정 형식:

1. **사실:** 코드, 기록, 인터뷰에서 확인된 것만 쓴다.
2. **이유:** 그래서 왜 되는지 또는 왜 안 되는지.
3. **남은 인사이트:** 이 프로젝트에서 건질 것 (재사용할 코드, 배운 점, 검증된 가정).
4. **권고:** 피봇·축소 / 접기 / 일단 출시 가운데 하나를 권하고, 근거를 한 줄로 단다.

문체 규칙:

- "~일 수도 있어요", "아마도", "어떻게 보면" 같은 표현을 쓰지 않는다.
- 접어야 할 프로젝트라면 왜 안 되는지 분명히 말한다.
- 최종 선택은 사용자가 한다. 스킬은 권고를 숨기지 않는다.

**완료 조건:** 사용자의 선택이 상태 파일에 기록됨.

### 3. 첫 결제 경로

선택에 따라 첫 결제까지 가는 최단 경로를 짠다.

- **팔 것:** 한 문장 가치 제안(영어), 대상 고객 한 집단(영어권)
- **가격과 결제 수단:** 가장 빨리 붙일 수 있는 방법 (결제 링크 수준부터 검토). 글로벌(미국) 기준으로 잡는다: 가격은 달러, 결제 수단 선택은 §6의 결제 연동 규칙을 따른다.
- **최소 범위:** 결제 1건에 필요 없는 기능은 명시적으로 뺀다
- **첫 고객 후보:** 실제로 연락하거나 노출할 채널과 사람, 구체적으로. 채널은 대상 고객이 실제로 모이는 영어권 채널에서 고른다.
- **수요 확인:** 더 만들기 전에 한다. 결제 링크는 결제 계정이 있어야 만들 수 있으므로 두 부분으로 나눈다.
  - 이 단계에서 하는 것:
    - 제품 이름과 핵심 키워드로 검색해 같은 이름의 제품과 겹치는지 확인한다.
    - 경쟁자가 많다는 사실을 수요의 증거로 치지 않는다.
    - 처음 연락할 사람을 이름으로 적는다. 후보가 없는 경로는 승인을 요청하지 않는다.
  - 두 번째 마일스톤으로 하는 것:
    - 돈을 낼 의사를 가장 싼 방법으로 확인한다. 결제 링크 하나로 먼저 받아 보는 것이 기본이다.
    - 첫 고객 열 명은 손으로 구하고, 그들이 한 말을 그대로 `state.md`에 적는다.
    - 정해 둔 날짜에 결과를 보고 계속할지 정한다. 낼 사람이 없으면 실행 레이어를 끄고 단계 2로 돌아간다.
- **마일스톤:** 3~5개. 각각 완료 조건과 목표 날짜를 단다.
  - 첫 마일스톤은 결제 계정 신청과 결제 링크다(§6 결제 연동 규칙).
  - 두 번째 마일스톤은 위의 수요 확인이다.
  - 결제 링크에 필요한 것 이상을 만드는 일은 그 뒤에 한다.

**완료 조건:** 사용자가 경로를 승인함. 승인되면 실행 레이어를 켠다.

### 4. 실행 루프

마일스톤을 작업 단위로 쪼갠 뒤 하나씩 처리한다.

```
작업 선택 → 스킬 라우팅(§6) → 실행(실행 레이어 또는 직접) → 오케스트레이터 검증 → 상태 갱신
```

- 검증은 실제로 확인한다. 빌드, 실행, 배포 URL 접속, 결제 테스트 모드 등.
- 막히면 §6의 디버깅 절차를 따른다. `.revive/architecture.md`의 핵심 흐름에서 끊긴 지점부터 짚고, 그 노드에 달린 파일을 읽는다.
- 구조가 바뀌는 작업(모듈 추가·삭제, 외부 서비스 연동)을 마치면 도식을 고친다.
- 출시 마일스톤은 §6의 출시 전 점검을 통과해야 완료로 친다.
- 사용자 승인이 필요한 일(결제 계정 개설, 배포 도메인 구매, 외부 게시)은 사용자에게 넘긴다.

### 5. 체크인

- 세션을 시작할 때마다 상태 파일을 먼저 읽고 한 줄로 요약한다: 지난번 진행, 지금 막힌 것, 다음 작업.
- **재정체 감지:** 마지막 진전 후 7일이 지났거나, 같은 작업이 두 번 연속 미완이면 단계 1로 돌아가 짧게 재진단한다.
  - 예외: 결제 계정 심사처럼 외부의 승인을 기다리는 작업은 재정체로 치지 않는다. 대기 사유와 시작일을 `state.md`에 적고, 그동안 다른 작업을 진행한다.
  - 재진단 뒤: 결정적 원인이 그대로면 기록하고 단계 4로 돌아간다. 원인이 바뀌었으면 실행 레이어를 끄고 단계 2와 3을 다시 한다.

### 종료

- **첫 결제 확인:** 결제사 대시보드에서 실결제(테스트 모드 아님)가 성공했고, 결제한 사람이 본인·지인·가족이 아니라고 사용자가 확인하면 첫 결제로 친다. 그다음 회고 문서를 쓴다. 무엇이 결정적 원인이었고 무엇이 풀었는지 정리한다. 배포판을 개선하는 데이터로도 쓴다.
- **접기 선택:** 판정 문서와 남은 인사이트를 회고로 남기고 종료한다.

## 5. 상태 파일

위치: 대상 레포의 `.revive/` 폴더

| 파일 | 내용 |
|---|---|
| `state.md` | 현재 단계, 확인된 사실, 결정적 원인, 사용자 선택, 마일스톤과 진행, 마지막 진전 날짜, 다음 작업, 읽을 외부 자료(`sources`), 실행 레이어 켜짐 여부, 고객이 한 말, 문체 프로필, 결제 경로와 그 확인 결과, 거절한 설치 제안, 외부 승인 대기(사유와 시작일) |
| `architecture.md` | 코드 전체와 아키텍처 도식(Mermaid), 노드별 근거 파일과 상태, 비효율·개선 후보 목록 |
| `verdict.md` | 판정 문서 (사실 / 이유 / 남은 인사이트 / 권고 / 선택) |
| `log.md` | 세션별 한 줄 기록 (날짜, 한 일, 막힌 것)과 작업별로 쓴 스킬 |
| `checks.md` | 출시 전 점검 결과 (항목별 통과 여부, 확인한 날짜, 확인한 주체) |
| `retro.md` | 종료 시 회고 |

- 사람이 읽을 수 있는 Markdown을 기본으로 한다. 기계가 읽을 필드는 `state.md` 상단 frontmatter에 둔다.
- `.revive/`를 git에 커밋할지는 사용자가 정한다. 기본값은 커밋하는 쪽이다(여러 기기에서 이어가기 위해).

## 6. 스킬 라우팅

근거: 조사 보고서 `reports/Revive 슬롯별 스킬 후보 조사.md` (2026-11-22). 보고서의 한국 전용 내용은 기준 시장 결정(§1)에 따라 뺐다.

### 원칙

- **Revive가 유일한 절차 층이다.** 함께 배포하는 스킬은 Revive가 단계에 맞춰 이름으로 부르는 부품이다. 다른 절차 묶음(프로세스 팩)은 넣지 않는다.
- **Revive의 완료 조건이 스킬의 규칙보다 우선한다.** 스킬이 다른 순서나 범위를 요구해도 §4 각 단계의 완료 조건과 단계 3의 최소 범위를 따른다. 스킬을 부를 때마다 그 작업의 완료 조건과 범위를 먼저 넘긴다.
- **적게 묶는다.** 함께 배포하는 스킬은 열 개 미만으로 둔다.
- **동의 없이 설치하지 않는다.** 설치되지 않은 스킬은 제안만 한다.
- 작업마다 어떤 스킬을 썼는지 `log.md`에 남긴다.

### 고르는 순서

슬롯마다 아래 순서로, 해당하는 것을 모두 쓴다. 앞 순서를 건너뛰지 않는다.

1. Revive가 직접 쓴 절차가 있으면 그 절차를 먼저 실행한다.
2. 함께 배포한 스킬이 있으면 그 스킬로 실행한다.
3. 선택 설치 스킬이 깔려 있으면 쓴다. 깔려 있지 않으면 설치를 제안한다.
   - 제안할 때 그 스킬에 딸린 훅, 네트워크 요청, 추가 비용을 함께 알린다.
   - 사용자가 거절하면 `state.md`에 적고 같은 스킬을 다시 제안하지 않는다.
4. 2번과 3번에서 쓸 스킬이 하나도 없으면 공식 문서를 확인한 뒤 스킬 없이 구현한다.

스킬 감지와 설치 제안은 오케스트레이터가 한다. 실행 레이어에는 쓸 스킬의 이름을 넘긴다.

### 빌드·의존성 복구

정찰에서 빌드나 실행이 실패했다면 실행 루프의 첫 작업으로 복구한다.

1. 정찰에서 기록한 실패 내용(명령, 오류 메시지)에서 출발한다.
2. 런타임과 패키지 관리자의 버전을 프로젝트가 멈춘 시점의 설정 파일에 맞춘다.
3. 그래도 실패하면 오류가 난 의존성만 올린다. 한꺼번에 전부 올리지 않는다.
4. 빌드와 실행이 되면 멈춘다. 복구와 무관한 개선은 하지 않는다.

### 디버깅 절차

Revive가 직접 쓴 짧은 절차로 처리한다. 디버깅 스킬은 넣지 않는다.

근거는 두 가지다. 널리 쓰이는 디버깅 스킬 둘을 스킬 없는 요청과 비교한 글에서 세 방식의 해결 수가 같았다. 다만 그 글은 한 사람이 버그 15개로 해 본 비교이고, 글쓴이가 자기 평가 도구를 홍보하는 글이다. 또 Reddit에서 오래 남는 스킬은 직접 쓴 좁은 절차라는 조언이 반복됐다.

1. `.revive/architecture.md`의 핵심 흐름에서 끊긴 지점을 짚는다.
2. 문제를 재현한다.
3. 원인을 확인한다. 추측으로 고치지 않는다.
4. 가장 작은 수정을 한다.
5. 오케스트레이터가 독립적으로 검증한다.

### 출시 전 점검

출시 마일스톤의 완료 조건은 아래 항목의 통과다. 결과는 `.revive/checks.md`에 항목별로 적는다.

스크립트로 확인하는 항목. 통과 여부는 모델의 판단이 아니라 스크립트 결과로 정한다.

1. 빌드된 JS 번들에서 비밀 키 문자열을 검색한다.
2. 커밋 이력 전체를 시크릿 스캐너(gitleaks 등)로 훑는다. 한 번이라도 올라간 키는 교체한다.
3. 세션 없이 각 API 경로에 요청을 보낸다. 보호되어야 할 경로에서 정상 응답이 오면 실패다.
4. 테스트 계정 둘을 만들어 한쪽 요청에 다른 쪽 ID를 넣는다. 남의 데이터가 보이면 실패다.
5. Supabase를 쓰면 `service_role` 키가 클라이언트에 없고 RLS가 켜져 있는지 확인한다.

사용자가 확인하는 항목. 사용자가 직접 보고 답한 내용을 적는다.

6. 유료 API 제공자 대시보드에 지출 상한이 걸려 있다.
7. 유료 API를 부르는 경로마다 인증과 사용자별 호출 제한이 있다. 코드에서 확인할 수 있는 부분은 에이전트가 먼저 확인한다.

그 밖의 점검:

- **독립 리뷰어:** 새 컨텍스트의 읽기 전용 에이전트가 전체 변경을 검토한다.
- **`/security-review`:** 최소한의 확인으로만 쓴다. 이 명령은 커밋하지 않은 변경만 본다. 되살린 프로젝트의 기존 코드는 대상이 아니므로, 실행 루프에서 새로 만든 변경에 대해 커밋 전에 돌린다. 변경이 크면 인증, 입력 처리, DB처럼 영역별로 나눠 돌린다.
- **화면 회귀:** 디자인을 바꾸기 전후에 360px 모바일 화면과 키보드 탭 순서를 기록해 비교한다.
- **약관 페이지:** 약관(Terms), 개인정보처리방침(Privacy Policy), 환불 규정(Refund Policy) 페이지가 있는지만 확인한다. 결제사가 가입 심사에서 이 페이지들을 볼 수 있다. 내용의 법적 검토는 하지 않는다(§2).

### 결제 연동 규칙

결제는 글로벌(미국) 판매자를 기준으로 안내한다.

- **기본 경로:** Stripe. 코드 없이 붙는 결제 링크부터 검토하고, 필요할 때만 체크아웃을 연동한다.
- **대안 경로:** 판매 대행 방식(Merchant of Record). 사용자가 Stripe 계정을 열 수 없거나 세금 처리를 결제사에 맡기려 할 때 쓴다. Polar를 먼저 검토하고, 그다음이 Paddle이다.
- **확인 순서:**
  1. 사용자에게 Stripe 계정을 열 수 있는지 묻는다.
  2. 열 수 없으면 대안 경로로 간다.
  3. 대안 경로도 안 되면 Freemius와 Stripe Managed Payments를 선택지로 알린다. 둘 다 Revive가 확인하지 않은 선택지라고 밝힌다.
  4. 그래도 안 되면 Revive 범위 밖이라고 알리고 사용자가 직접 결제 수단을 정한다.
  5. 답과 정한 경로를 `state.md`에 적는다.
- **대안 경로의 주의:** 판매 대행 결제사마다 가입 거절과 정산 지연 사례가 있다.
  - 결제 계정 신청은 첫 결제 경로의 첫 마일스톤으로 잡는다. 심사에 시간이 걸린다.
  - 연동이 끝난 것으로 결제 준비가 끝났다고 치지 않는다. 첫 정산을 받아야 확인된다.
- **스킬 사용:** Stripe와 Polar의 공식 스킬을 쓴다. 복사본은 빨리 낡으므로 Revive에 넣지 않고 실행 시점에 설치를 제안한다. 스킬이 없으면 공식 문서를 확인한 뒤 구현한다.
- **다루지 않는 것:** 한국 전용 절차(국내 PG 심사, 사업자등록, 원화 정산), 세금 신고 방법. 두 경로의 차이는 "세금 처리를 누가 하는가"까지만 설명한다.
- **사용자에게 넘기는 일:** 결제 계정 개설, 본인 확인, 정산 계좌 연결.
- **제외·보류:**
  - Lemon Squeezy: 서비스 종료가 예정되어 제외한다.
  - Dodo: 잔액을 보류한 뒤 몰수했다는 사용자 글이 한 건 있어 보류한다.
  - Creem: 사용자 근거가 거의 없고 초대제라는 답을 받은 사례가 있어 보류한다.

### 묶음 구성과 배포 방식

- **복사해서 넣는 것:** 훅, 바이너리, 네트워크 호출이 없고 라이선스가 재배포를 허용하는 마크다운 스킬만 넣는다. 지금은 슬롯별 구성 표의 "함께 배포" 열에 있는 6개다.
- **복사할 때 확인할 것:**
  - 업스트림의 특정 커밋에서 가져온다.
  - 스킬 폴더 안의 `references/` 폴더까지 함께 가져온다.
  - 복사 직전에 그 폴더에 훅과 실행 스크립트가 없는지 다시 확인한다. marketingskills는 이 확인을 아직 하지 않았다.
  - 본문에 협찬사 언급이 있으면 뺀다(`launch`에 있다는 조사 기록이 있다).
  - 스킬 목록에 실리는 설명은 짧게 쓴다.
- **기록:** 플러그인 루트의 `BUNDLED_SKILLS.md`에 스킬마다 업스트림 커밋 SHA, 마지막으로 검증한 날짜와 모델, 그 스킬이 막으려는 실패를 적는다.
- **재검증:** 새 모델이 나오면 유지보수자가 스킬 없는 실행과 비교한다. 낫지 않으면 뺀다.
- **설치를 안내하는 것:** 훅이나 바이너리가 딸린 스킬(Impeccable, `security-guidance`)과 빨리 낡는 결제사 스킬. 깔려 있으면 감지해서 쓴다.
- **호출만 하는 것:** 내장 명령(`/security-review`).
- **플러그인 `dependencies`는 쓰지 않는다.** 의존 플러그인이 꺼지면 Revive도 꺼지기 때문이다.
- **고지:** 복사한 스킬 옆에 업스트림 LICENSE를 두고, 루트의 `THIRD_PARTY_NOTICES.md`에 모은다(§7).

### 확인하지 않은 것

- 어떤 스킬도 직접 실행해 비교하지 않았다. 위 구성의 근거는 스킬 문서와 사용자 경험담이다.
- 오케스트레이터와 실행 레이어 세션이 다른 플러그인의 스킬을 안정적으로 부를 수 있는지 시험하지 않았다. 고르는 순서의 3번이 여기에 달려 있다.
- Stripe 공식 스킬 가운데 어느 것이 결제 링크 수준의 첫 결제에 맞는지 본문을 읽지 않았다. 저장소에는 `stripe-best-practices`, `stripe-implementation-planner`, `stripe-pay`, `stripe-docs` 등이 있다.
- Freemius와 Stripe Managed Payments의 가입 조건과 에이전트 스킬 유무를 확인하지 않았다.
- 영어권 출시 채널은 조사하지 않았다.
